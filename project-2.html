背景与角色

重复劳动不只在检索；每份报名的材料重拼也在消耗时间。

场景
投标报名要准备的材料大部分固定，项目名称、日期与排列顺序每份不同。
代价
每次逐项重拼，重复劳动多，且容易漏件。
形态
一条 Dify 工作流：10 个节点、12 条连线、4 个代码节点。
输入 / 输出
输入为一张公告截图；输出为确认单与报名资料 Word。

01

单一真相源

改前：公司信息分散在 6 个模板里，改一处要回改六处，容易漏改。改后：真值只放一份 JSON，模板内只留占位符，配模板校验脚本，6/6 通过。

02

先摘录后结构化

材料名先从公告原文逐字摘录，再只从摘录里拆条目；每条带原文依据。评测集召回 100%，编造 0。

文档服务：本机 8090 端口；结果汇总读取真实返回，避免「看着成功、文件没出」的假绿灯。

01

内网可访问

服务当前只监听本机；换到内网常开机器并开放端口后，同事可访问。

02

不用装任何东西

浏览器上传与下载即可。

03

无繁杂信息

确认单五状态写明缺什么。

04

出错能查日志

有 /health 与日志，无告警。

可行路径

放入一台常开机的内网机器，用 Dify 的 WebApp 分享做入口，并配一页 SOP。

不做什么 · 为什么

不上公网云主机：生成的文档涉及公司资料；不设人工确认关口：该场景要的是批量出件。

07 / 07

取舍与故障

模型选型按数据敏感度定；故障记录保留定位过程。

如果向量化走云端 API

省内存、上手快；但知识库里的模板与证照说明要往外发。按次计费，网络一断检索就停。

→

现在：本地 Ollama ＋ bge-m3

1024 维；模板与证照文本留在内网，零调用成本，中文效果够用。代价是约占 1.2 GB 内存。

补充：读公告截图那一步走云端多模态 —— 公开的公告走云端，公司资料走本地，按数据敏感度分开定。

怎么处理

一个 300 字的模板被切成 3 段，召回只回来半张卡

先查分隔符设置，再用平台自己的切块类做对照，最后读切块源码

切块只按 # 标题行划分；把模板里的标题标记去掉，14 个文件稳定产出 14 段。

三个回归用例同时返回 0 条，代码没动过

失败点都停在第一个大模型节点，供应商返回 400；同类错误复现两次即排除自身改动

确认是外部账号额度问题；恢复后重跑，条数是 14 / 12 / 9。

合并后首次试运行，HTTP 节点返回 422，工作流 partial-succeeded，file_path 为空

同一份 body 本地回放 200，排除服务端；变量里的换行和引号把 JSON 拼坏，平台 repair 把对象修成数组

请求体改由代码节点 json.dumps 生成，HTTP 节点用 raw-text 原样发出；服务端对非对象 body 回 400，体检脚本加 Body 类型护栏。

说明：文档服务跑在内网常开机的机器上，未上公网；链路里没有人工确认关口 —— 该场景要的是批量出件。
